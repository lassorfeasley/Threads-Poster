North star

Keep improving the product as a local web UI (easy UX iteration). Host the dashboard so other people can use it without running Python — media creation stays local (Mac app) or becomes upload-your-own. Longer term: optional always-on publishing, shared workspaces, and fuller autopilot. Prefer a hosted web app over Mac App Store; do not plan a Swift rewrite.

Autonomy goal: the app can operate a Threads account (queue, schedule, engage) with human taste checks as needed. Local media creation and cloud/always-on publishing can stay split — same shape as today's local factory + headless publisher.

Phase 1 — Host the dashboard

Put the FastAPI app on the internet so a second person can use it without cloning the repo. The dev loop stays local (python run.py dashboard); hosted is a deploy target, not a dev environment. Media creation (yt-dlp, ffmpeg, Whisper) stays local or becomes upload-your-own — the hosted app never downloads YouTube videos. Deliberately deferred (Aug 2026): finish the Phase 0 latency pass first — hosting won't fix UI latency (the cost is remote-Postgres round trips, which a hosted UI pays too), and there's no second user waiting yet.

  • Next
    Deploy the dashboard to Fly (or Railway / Render) The same FastAPI + Jinja app that runs locally, served over HTTPS. Already talks to Postgres and Supabase — no SQLite dependency on the server. One Fly app per workspace (or a single app with workspace routing). Add a Dockerfile.web and an [http_service] block. Config files (workspaces/<slug>/config/) ship in the image; secrets come from fly secrets set. The existing Fly scheduler workers keep running alongside.
  • Next
    Auth gate (even for one user) The dashboard has no login today — it binds to 127.0.0.1 and trusts the operator. Hosting it means adding an auth wall before anything else goes public. Simplest v1: a single shared password or invite-only magic link (no user model yet). Just enough to keep the internet out while you use it yourself over HTTPS.
  • Next
    Real HTTPS OAuth callback (kill paste-code) Pulled forward: it's a small, independent cloud endpoint with a solo payoff today — it kills the paste-the-?code= ritual on Connections — and App Review needs it anyway for a reviewable demo. Replace "authorize → broken localhost page → paste ?code=" with a hosted redirect (e.g. https://yourproduct.com/threads/callback) that exchanges the code server-side. Becomes trivial once the dashboard itself is hosted — the callback is just another route.
  • Later
    Upload-your-own-clip flow Today clips are created locally (download → trim → subtitle → export → upload to Supabase). A hosted user with no local pipeline needs a way to bring their own video: upload a file, write a caption, queue it. The triage/trim/subtitle workflow stays local-only for now; this just adds a "bring a finished clip" entry point so the hosted dashboard is useful on its own for someone who already has video.
  • Later
    White-label the clip output App name and logo already ship on Brand & audience; what remains is the clip's look — subtitle colors and the bundled Funnel font are still the Renewables.org look, hardcoded in settings.yaml / app/subtitles.py. Per-workspace colors and fonts only pay off when someone else runs the app, so this sits with distribution, not Phase 0.
Phase 1b — Mac app (optional, parallel track)

Same local pipeline; hide the plumbing. Only matters if local media creation needs to ship to non-developers. Not a prerequisite for multi-user — the hosted dashboard is.

  • Later
    Package with Tauri, Electron, or py2app Double-clickable .app that starts the Python backend and shows this UI (WebView or window). Bundle ffmpeg / yt-dlp; download Whisper weights on first run if needed. Sign + notarize for Gatekeeper.
  • Later
    Auto-update (in the very first distributed build) Electron-updater, Tauri updater, or Sparkle (if py2app). Non-negotiable from build one: retrofitting an updater onto installs that lack it is the real nightmare scenario. With it, the fleet converges on a fix in hours-to-days — the closest a distributed app gets to a web deploy. Direct download (site / Gumroad / etc.), not App Store as the default.
  • Later
    Release discipline (the actual cost of being an app) The dev loop stays the browser app — packaging is a distribution artifact, not a dev environment. One-time: signing, notarization, and a build pipeline. Per release: smoke-test the signed artifact on a clean machine (bundled-Python paths, Gatekeeper, arm64 + Intel), and keep DB migrations additive / forward-safe (already the _ensure_new_columns habit) since updates run against customers' existing app.db. Add a log-export / diagnostics button once there are users on machines we can't see.
Meta / Threads for customers (prerequisite for anyone else's account)

Today's flow is single-operator + tester invite + paste OAuth code from https://localhost/…. Productized, that admin stays with us once; customers only do OAuth consent. Sequencing decision: stay in tester mode and improve the product solo; trigger App Review when a real second user appears. Approval is likely — these scopes are the textbook third-party publishing bundle, and review judges permission usage shown in a working demo, not where the content comes from — but budget one resubmission cycle.

Bigger risk than review: posting broadcasters' footage is an account-level IP exposure (complaints / strikes against the Threads or Instagram account), independent of API approval — and amplified once customers pick the source channels. Also: Reels require the customer's Instagram account to be a (free) professional account; Threads takes any normal account.

  • Later
    One product Meta app + App Review + publish Leave "testers only." Get Advanced Access / review for the scopes we already use: threads_basic, threads_content_publish, threads_manage_replies, threads_read_replies, threads_manage_insights. Use the Threads app ID/secret (not the generic Meta app ID). Platform checklist: privacy policy URL, data-deletion callback/instructions, deauthorize callback, app icon, plus a demo/screencast showing every permission in use. Business Verification has weeks of lead time (documents, possibly an entity) — start that paperwork one step earlier than feels necessary; it parallelizes for free. After publish, any Threads user can authorize — no tester role.
  • Later
    Customer Threads connect (no Meta Developer for them) Customers click Connect Threads, log in with their normal Instagram/Threads account on Meta's consent screen, and grant permissions — like "Sign in with Google." They never open developers.facebook.com, create an app, copy secrets, register redirect URIs, or accept tester invites. You own one product Meta app; App ID/Secret stay server-side.
  • Later
    Per-workspace (or per-user) token storage Stop the single global AppToken(name="threads"). Store long-lived Threads tokens keyed by workspace/user + Threads user id; keep refresh (~60d tokens, refresh when stale). Headless publish (Fly / Actions / scheduler) uses that workspace's token. Enforce Threads' ~250 API posts / 24h per profile in product UX.
  • Later
    Product account vs Threads connection Optional light product login (license key or email) for the workspace; Threads remains a connected integration, not the product identity. Same pattern later for YouTube if needed.

  • No

Architecture: what runs where

Today you never "installed a companion" because you are the runtime (python run.py dashboard). The product already splits into a local factory (yt-dlp, ffmpeg, Whisper — heavy, on your Mac) and headless cloud services (scheduler on Fly, monitor on Actions — light, always on). Hosting the dashboard is the next layer: the same FastAPI app, served over HTTPS, talking to the same Postgres and Supabase it already uses. The dev loop does not change — python run.py dashboard stays the development environment; the hosted deploy is a build artifact.

Customers should not need Meta Developer setup or multiple product accounts for the core loop — Threads (and later YouTube) show up as connected integrations on one workspace after a normal OAuth consent.
