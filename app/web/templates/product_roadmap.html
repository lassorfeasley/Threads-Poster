North star

Split the product in two and host the half that can be hosted. The factory (download, trim, subtitle, export, upload) is pinned to the operator's own Mac by ffmpeg, Whisper, and a residential IP. The control room (triage, queue, calendar, analytics, connections, engagement) is database reads and API calls, and can run anywhere. Today they are one FastAPI process; the Fly scheduler already proves the control-room half runs detached, because it publishes from Supabase signed URLs without touching a local file. Prefer a hosted web app over Mac App Store; do not plan a Swift rewrite.

Autonomy goal: the app can operate a Threads account (queue, schedule, engage) with human taste checks as needed. Local media creation and cloud/always-on publishing stay split — same shape as today's local factory + headless publisher.

Critical path — first paying customer

Target shape: 5–15 hand-onboarded paying users who run the local factory themselves and reach a hosted control room over HTTPS. Four tracks, mostly parallel. Track A is first only because it is the one that runs on someone else's clock — every day it is not started is a day added to the end.

Phase 1 — Host the dashboard

Put the FastAPI app on the internet so a second person can use it without cloning the repo. The dev loop stays local (python run.py dashboard); hosted is a deploy target, not a dev environment. Media creation (yt-dlp, ffmpeg, Whisper) stays local — the hosted app never downloads YouTube videos. Un-deferred Sept 2026. The August deferral rested on two things that are no longer true: that there was no second user waiting, and that hosting could not help latency. There are users now, and hosting can help latency — the August reasoning assumed the round trip had to stay expensive, when the actual problem is that nothing is colocated with anything (see B1).

  • Next
    Deploy the control room to Fly — not Vercel The same FastAPI + Jinja app that runs locally, served over HTTPS. Already talks to Postgres and Supabase — no SQLite dependency on the server. One Fly app per workspace. Add a Dockerfile.web and an [http_service] block. Config files (workspaces/<slug>/config/) ship in the image; secrets come from fly secrets set. The existing Fly scheduler workers keep running alongside. Vercel is ruled out on architecture, not preference. Request handlers fork daemon threads via _in_background that deliberately outlive the response, and boot already reconciles the ones that die; serverless would kill every one of them. pagecache is in-process memory shared across requests, so a function-per-request model discards exactly the thing that makes list pages fast. And the media stack (ffmpeg, yt-dlp, faster-whisper) is not a serverless bundle. Fly is also already proven here — the schedulers have run on it for months.
  • Next
    Auth gate — the hard prerequisite The dashboard has no login of any kind today: it binds to 127.0.0.1 and trusts whoever is at the keyboard. (threads_api.is_authenticated() sounds like auth but only means a Threads token exists.) Nothing goes on the public internet before this lands. Design in the Auth & control plane card below.
  • Next
    Real HTTPS OAuth callback (kill paste-code) Pulled forward: it's a small, independent cloud endpoint with a solo payoff today — it kills the paste-the-?code= ritual on Connections — and App Review needs it anyway for a reviewable demo. Replace "authorize → broken localhost page → paste ?code=" with a hosted redirect (e.g. https://yourproduct.com/threads/callback) that exchanges the code server-side. Becomes trivial once the dashboard itself is hosted — the callback is just another route.
  • Later
    Upload-your-own-clip flow Today clips are created locally (download → trim → subtitle → export → upload to Supabase). A hosted user with no local pipeline needs a way to bring their own video: upload a file, write a caption, queue it. The triage/trim/subtitle workflow stays local-only for now; this just adds a "bring a finished clip" entry point so the hosted dashboard is useful on its own for someone who already has video.
  • Later
    White-label the clip output App name and logo already ship on Brand & audience; what remains is the clip's look — subtitle colors and the bundled Funnel font are still the Renewables.org look, hardcoded in settings.yaml / app/subtitles.py. Per-workspace colors and fonts only pay off when someone else runs the app, so this sits with distribution, not Phase 0.
Auth & the control plane

Use Supabase Auth, not an edge proxy. supabase>=2.5 is already a dependency and every workspace already has a project, so the auth system is provisioned and idle. Cloudflare Access was considered and dropped: it authenticates at the edge, which means it sits in front of every route indiscriminately and Meta's and Stripe's server-to-server callbacks would hit a login page. In-app auth makes that a per-route decision instead of a bypass policy, and it leaves behind a user table — which billing needs anyway.

  • Next
    One auth-only Supabase project as the control plane A single project holding users, workspaces, and subscriptions — who exists, what they own, whether they have paid, and which data project their workspace lives in. Each tenant keeps a separate project for their own data (see Tenancy). JWTs verify locally against a signing secret, so the auth project never has to be the data project. Three payoffs: one login across every deployment for support, customer accounts that survive consolidating the data layer later, and a natural home for Stripe's subscription state.
  • Next
    Login route + session middleware A Jinja /login form, a server-side sign_in_with_password(), and a signed HTTP-only cookie holding the access token. Middleware decodes the JWT and redirects when it is missing or expired. Verification is local (jwt.decode against the project secret), which matters in an app that already pays for too many round trips. Note the friction: Supabase's documented path assumes the JS client manages tokens in the browser, and this is server-rendered Jinja, so the session glue is hand-written rather than copy-pasted.
  • Next
    The unauthenticated allowlist Four kinds of route must skip the session check and verify a signature instead: the Threads/Instagram OAuth callback, Meta's deauthorize callback, Meta's data-deletion callback, and the Stripe webhook. Getting this wrong fails App Review quietly (Meta's servers see a login page) and drops payment events silently. Worth one explicit list in code rather than a decorator people forget.
Billing — Stripe

Hosted everything: Stripe Checkout for starting a subscription, Stripe Customer Portal for changing or cancelling one. No card data touches the app, no PCI scope, and no billing UI to build or maintain — two redirects and a webhook. Depends on the entity (Stripe needs business details before it pays out) and on the control plane (subscription state needs a table to live in).

  • Next
    C1. Checkout + Customer Portal One product, one recurring price to start. Signup redirects to a Stripe-hosted Checkout session; a billing page in the dashboard redirects to the Portal for payment method, plan changes, invoices, and cancellation. Both are configuration, not code. Keep test-mode and live-mode keys per environment so a staging deploy can never charge anyone.
  • Next
    C2. Webhook endpoint Unauthenticated by necessity, signature-verified without exception, and on the allowlist above. Handle checkout.session.completed (activate, provision), customer.subscription.updated and .deleted (state changes), and invoice.payment_failed (start the grace period). Store stripe_customer_id and subscription_status on the workspace row in the control plane. Make handlers idempotent — Stripe retries, and a double-provision is worse than a missed one.
  • Next
    C3. Decide what lapsing actually does This is a product decision, not a Stripe one, and it deserves to be made deliberately rather than discovered. Proposal: a failed payment shows a banner and starts a grace period; a cancelled subscription makes the scheduler skip that workspace and the dashboard read-only, but never deletes the queue or the media. Silently dropping a queued post is the one failure this product cannot afford — someone's content calendar has a hole in it and no error to point at.
  • Later
    Provisioning on payment, and tax Wire checkout.session.completed to actually create the workspace rather than notifying you to do it by hand — worth automating around the fifth customer, not the first. Stripe Tax once there are customers in more than one jurisdiction.
Tenancy — deliberately deferred

Decision (Sept 2026): keep one Supabase project per tenant for the first few customers. A project beyond the first runs on the order of ten dollars a month, so one subscription covers several customers' databases — at three users, separate projects cost less than the engineering time to avoid them, and they buy total schema freedom while Instagram, LinkedIn, and the scheduling model are all still moving. The forcing function is somewhere around eight to ten users. Revisit then, not now.

Recorded so the eventual decision does not start from scratch. Two candidate models: schema per tenant in one project (isolation enforced by Postgres, so a forgotten filter cannot leak; every migration becomes a loop over schemas with no single transaction) or a workspace_id column on shared tables (one DDL per change, but tenant scoping becomes a discipline paid on every query written from then on). Schema translation must use SQLAlchemy's schema_translate_map, never SET search_path — the Supabase transaction pooler on port 6543 reuses backends across transactions, so session state leaks between tenants. One product argument favors shared tables: TraitWeight sits in collecting for months on a new account, and aggregate priors across customers would fix that cold start.

  • Blocker
    What breaks the day the databases merge No table in app/models.py has a tenant column. AppToken uses name as its primary key, so AppToken(name="threads") can exist once per database — customer two's token would overwrite customer one's. SchedulerState and AnalyticsDigest are documented singletons. Four unique constraints collide across tenants: Candidate.video_id and Channel.channel_id (two customers in one niche watching the same channel is the expected case, not an edge case), Trait.name, and TraitWeight(trait, metric) — the last silently trains one customer's ranking on another's results.
  • Later
    Config has to leave the filesystem Six YAML files per workspace under workspaces/<slug>/config/, four of them written back from UI pages. A shared database does not help while settings.yaml is a file beside the process. Note the interaction with latency: load_settings() is called 100+ times per calendar render and is cached on file mtime, so moving it to Postgres naively turns a stat() into a round trip. It needs a real cache before it moves.
  • Later
    One process serving many tenants The end state, and the expensive part. app/config.py resolves WORKSPACE at import and derives CONFIG_DIR and DATA_DIR as module-level constants, so every importing module holds a frozen path. Unwinding that into request-scoped context is the real multi-tenancy project. The models survive both phases unchanged, which is the point — the plumbing gets done twice at most, the schema never.
Phase 1b — Mac app (optional, parallel track)

Same local pipeline; hide the plumbing. Only matters if local media creation needs to ship to non-developers. Not a prerequisite for multi-user — the hosted dashboard is. Meta / Threads for customers (prerequisite for anyone else's account)

Today's flow is single-operator + tester invite + paste OAuth code from https://localhost/…. Productized, that admin stays with us once; customers only do OAuth consent. The trigger has fired (Sept 2026): the previous plan was to stay in tester mode until a real second user appeared, and one has. Approval is likely — these scopes are the textbook third-party publishing bundle, and review judges permission usage shown in a working demo, not where the content comes from — but budget one resubmission cycle.

Why this is the real onboarding blocker rather than hosting or login: in tester mode every workspace needs its own developer app, which is why workspaces/climate/.env carries six Meta secrets. Onboarding one customer today means creating a Meta app, configuring the Threads and Instagram products, registering redirect URIs, and walking them through a tester invite — roughly an hour of console work per person, forever. At fifteen customers that is not an onboarding flow, it is a part-time job. One reviewed app collapses those six per-tenant secrets into one global pair and reduces onboarding to a consent screen.

Bigger risk than review: posting broadcasters' footage is an account-level IP exposure (complaints / strikes against the Threads or Instagram account), independent of API approval — and amplified once customers pick the source channels. Also: Reels require the customer's Instagram account to be a (free) professional account; Threads takes any normal account.

  • Next
    One product Meta app + App Review + publish Leave "testers only." Get Advanced Access / review for the scopes we already use: threads_basic, threads_content_publish, threads_manage_replies, threads_read_replies, threads_manage_insights. Use the Threads app ID/secret (not the generic Meta app ID). Platform checklist: privacy policy URL, data-deletion callback/instructions, deauthorize callback, app icon, plus a demo/screencast showing every permission in use. Business Verification has weeks of lead time and wants a registered entity behind the documents — that is A1 on the critical path, and it parallelizes for free. After publish, any Threads user can authorize — no tester role.
  • Next
    Real OAuth callback — one host, not one per tenant There is no callback route today: THREADS_REDIRECT_URI points at https://localhost/threads-callback, which resolves to nothing, and POST /threads/connect takes a hand-pasted ?code=. Meta requires every redirect URI to be registered explicitly, so per-tenant subdomains would mean a console entry per customer — reintroducing exactly the per-user admin chore App Review is meant to delete. Instead register one callback host (e.g. https://connect.yourproduct.com/threads/callback), carry the tenant in the OAuth state parameter, exchange server-side, and redirect back to their subdomain. Cheap to design in now, irritating to retrofit.
  • Next
    Deauthorize + data-deletion endpoints Both are App Review requirements and both are called server-to-server by Meta, with no browser and no session — they belong on the unauthenticated allowlist and must verify Meta's signed request. Deauthorize should revoke the stored token and stop that workspace's scheduler; deletion needs a documented path plus a status URL. Easy to leave until last and then discover they fail review.
  • Next
    Customer Threads connect (no Meta Developer for them) Customers click Connect Threads, log in with their normal Instagram/Threads account on Meta's consent screen, and grant permissions — like "Sign in with Google." They never open developers.facebook.com, create an app, copy secrets, register redirect URIs, or accept tester invites. You own one product Meta app; App ID/Secret stay server-side.
  • Later
    Per-workspace (or per-user) token storage Stop the single global AppToken(name="threads"). Store long-lived Threads tokens keyed by workspace/user + Threads user id; keep refresh (~60d tokens, refresh when stale). Headless publish (Fly / Actions / scheduler) uses that workspace's token. Enforce Threads' ~250 API posts / 24h per profile in product UX. Deferred by the tenancy decision: with one Supabase project per tenant, a primary-keyed AppToken is already one token per customer and this is not urgent. It becomes a hard blocker the day the databases merge — see Tenancy.
  • Later
    Product account vs Threads connection Optional light product login (license key or email) for the workspace; Threads remains a connected integration, not the product identity. Same pattern later for YouTube if needed.

Architecture: what runs where

Today you never "installed a companion" because you are the runtime (python run.py dashboard). The product already splits into a local factory (yt-dlp, ffmpeg, Whisper — heavy, on your Mac) and headless cloud services (scheduler on Fly, monitor on Actions — light, always on). Hosting the dashboard is the next layer: the same FastAPI app, served over HTTPS, talking to the same Postgres and Supabase it already uses. The dev loop does not change — python run.py dashboard stays the development environment; the hosted deploy is a build artifact.

Target end state, four planes. Factory — the customer's Mac: download, trim, subtitle, export, upload to Supabase Storage. Pinned there by ffmpeg, Whisper, and a residential IP (YouTube blocks datacenter IPs), and pinned there deliberately, since hosted downloading is out of scope below. Control room — Fly, one app per workspace: triage, queue, calendar, analytics, connections, engagement. Publisher — the existing Fly scheduler worker, unchanged. Control plane — one auth-only Supabase project: users, workspaces, subscriptions, and the map from a workspace to its data project. Data planes stay one Supabase project per tenant until roughly the eighth customer.

One consequence worth stating plainly: because customers need the factory, hosting does not remove their local install. It has to add value beside it — reaching the queue from a phone, publishing while the laptop is shut, and a UI that ships daily instead of per release. If the hosted half is only a mirror of what they already run, it is not worth the two deploy targets.

Customers should not need Meta Developer setup or multiple product accounts for the core loop — Threads (and later YouTube) show up as connected integrations on one workspace after a normal OAuth consent.
